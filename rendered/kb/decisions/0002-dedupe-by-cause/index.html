Problem A: month-first shared parser in day-first tenants

The shared parser interprets dates as month/day while the tenant writes day/month. For example, Harbour Dental’s app report R-41200 describes 7 April becoming 4 July; Lantern Row’s app report R-41203 describes 2 December becoming 12 February. The parser cohort covers app and email reports in day-first tenants, and form reports where the form does not introduce the booking-v3 hint defect.

Engineering ticket: GitHub #1 — parser. The source-of-truth count and scope appear in the computed table above. The cohort includes the unresolved observations listed below; it does not establish a parser root cause for every body. Preserve those caveats during follow-up.

Original verification proposal (not executed; engineering notice governs disposition): Test an unambiguous tenant date convention and an ambiguous numeric example such as 07/04/2026: the intended 7 April must remain 7 April in the invite. Test app, email and applicable booking-v2 form paths. The proposed parser and hint checks address different input paths.

Problem B: booking-v3 prints the wrong date-format hint

Booking-v3 prints MM/DD/YYYY for tenants whose form interprets dates in the tenant’s day-first convention. Following the hint supplies month first to a day-first form. This is a separate UI/input contract defect, even when its symptoms resemble the parser defect. The affected form reports come from Alder Physio, Copper Studio and Pale Harbour. App/email reports at those same tenants still belong in the parser cohort.

Examples: Copper Studio form report R-41230 and Alder Physio form report R-41241. Both were merged into #4471, but neither is resolved merely by changing the shared parser.

Engineering ticket: GitHub #2 — booking-v3 hint. Original verification proposal (superseded by form retirement): Check that displayed guidance, accepted input and resulting booking agree for each tenant locale. For a day-first tenant, entering 6 January according to the displayed guidance must preserve 6 January. Check both booking-v3 and booking-v2, with browser locale differing from the tenant locale.

  2. Read the body, look up the tenant locale and booking-form version, then identify the channel.
  3. Merge only when the observed behavior and verified context support the same cause.
  4. Keep unknown tenants, unexplained timing shifts and conflicting evidence separate for investigation.
  5. Retain original IDs and provenance. Update the issue’s count from distinct report IDs.
  6. Recheck this page when tenant forms, date parsing or the live queue change. Assign a review owner and date; this snapshot must not silently become a live count.
